# 模型是全局实体，映射与上游能力分离

## Status

Accepted.

后续修订：ADR 0017 把这里的“上游能力关系”改称为**上游模型绑定**，删除了上游名称覆盖名与 `priority`/`weight`；本 ADR 的分离结论不变。

## Context

把模型按上游拆成 catalog 条目，会让“模型可见性”“名称改写”“上游是否支持”混成一张表；名称映射还会被误当作路由声明。模型名本身是全局语言，上游只是执行名称改写和提供候选能力。

## Decision

- `Model` 是全局实体：公开模型名、启用状态和计费信息，不绑定上游。
- 名称改写只发生在绑定这一层：系统模型经绑定转换为上游实际认得的模型 ID（ADR 0017）。
- 上游是否支持某模型由显式的 `upstream_models` 能力关系决定；映射本身不产生候选。
- 某模型的候选必须同时满足 `upstream.enabled`、`upstream_models.enabled`、`weight > 0`；候选排序使用该关系上的 priority/weight。
- `/v1/models` 只返回全局启用且至少有一个正权重候选的模型。
- 没有正权重候选时返回明确错误并告警，不把请求发给不支持该模型的上游。
- `shutdown_date` 第一期只是公告元数据，不参与可见性或路由求值。

## Consequences

正面：

- 模型、名称改写、上游能力三者可以独立演进。
- 绑定不会意外把所有上游变成候选。
- 未来号池只需增加上游能力关系，不改变公开模型语义。

负面：

- 增加一层 upstream/model 能力关系，管理面需要同时维护模型和该关系。
- 只有映射、没有能力关系的模型不可调用。
- 需要额外的引用校验和候选一致性检查。
