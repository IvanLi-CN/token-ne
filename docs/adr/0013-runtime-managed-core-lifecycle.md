# 运行时管理全部核心实例

## Status

Accepted.

## Decision

Compose 只声明控制面、数据库、Caddy、网络和持久卷，不声明 core service。控制面启动时使用自身构建注入的产品版本登记同版本核心；当该版本没有运行中、预热中或进行中的部署时，控制面自动创建一个精确版本或 digest 的动态 core。控制面重启和 Dockrev 更新都会重复这一幂等检查，因此控制面与活动核心不会长期停留在不同产品版本。

Caddy 的初始 `/v1/*` 路由必须 fail-closed 返回 503；只有核心实例完成协议、配置、签名和心跳确认后，协调器才把它加入上游。版本升级仍允许旧版本和新版本在滚动切换期间短暂并行，旧实例在权重归零、spool 清空后停止并由控制面 prune；这段重叠是零停机切换的一部分，不是永久基线实例。

历史 Compose core 若没有 `com.token-ne.deployment` 标签，不再被接管或重新加入流量。它只能在权重为零时由重协调停止并标记为退休，之后按 spool 清空条件显式 prune；如果仍承载流量，协调器拒绝自动退休并报告冲突。

## Consequences

- 生产 Compose 更新不会再创建或保留一个与动态部署并列的基线 core。
- 新 API release 的精确同版本 core 自动部署；镜像拉取失败时 API 保持健康并留下结构化错误，已有活动版本继续承载流量；没有已受控核心时核心池返回 503，避免静默接流量。
- 首次启动和版本切换可能暂时没有可用核心；这是显式的 503，而不是把未确认配置的实例接入流量。
- 动态 core 仍使用 Docker Engine API、独立状态目录和 `restart=no`；Compose `down --remove-orphans` 仍不是单实例清理入口。

## Rejected alternatives

- 保留 Compose 基线 core：会让 `latest` 控制面和精确版本动态 core 形成永久版本分叉，并且基线容器容易与数据库实例记录漂移。
- 把动态 core 改为 `latest`：失去精确版本、digest 审计和可重复回滚能力。
- 启动时先停止旧核心再部署新核心：会放弃现有的分阶段切换和无停机回滚能力。
