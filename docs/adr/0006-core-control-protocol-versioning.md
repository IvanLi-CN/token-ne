# ADR 0006: 核心与控制面协议采用主版本路径和增量兼容

## Status

Accepted.

## Context

核心和控制面必须能跨版本共存：升级期间旧核心继续服务，新核心预热，控制面可能需要同时服务两个协议版本。协议既要容忍新增字段，又要在安全、路由和配置语义上严格校验。

可选方案：

- 无版本 JSON，靠字段探测。
- 单一全局版本，任何变更都强制同步升级。
- 主版本路径 + 独立配置 schema 版本 + 能力协商。

## Decision

- 控制接口使用 `/internal/v1/...`；破坏性变更新增 `/internal/v2/...`。
- `protocol_version` 管线路由、信封、错误格式；`config_schema_version` 管配置字段和语义，两者独立协商。
- 核心通过 `/internal/v1/meta` 和心跳声明协议版本、schema 范围、能力和构建信息。
- 同一主版本只允许新增可选字段、非安全枚举值和能力；安全、路由、认证枚举的新值必须由能力标记显式协商，控制面不得向未声明该能力的核心发送。不删除、不重命名、不改类型、不复用字段含义。
- 消费方忽略未知对象字段；未知的安全/路由/认证枚举拒绝，未知展示/行为枚举可映射为 `unknown` 并告警。
- 所有 `/internal/v1/*` 请求带协议版本和 request ID；配置按 revision 幂等，用量按 `event_id`/`batch_id` 幂等。
- 控制面只有确认协议兼容、schema 有交集、所需能力齐全、配置已应用后，才把核心加入 Caddy 上游。
- 完整契约见 [`../protocol.md`](../protocol.md)。

## Consequences

正面：

- v1/v2 可以在一段迁移期内共存，不需要同时重启所有核心。
- 新增字段不会破坏旧核心；严格校验仍能阻止危险语义。
- 配置 schema 和协议版本可以独立演进。
- 升级失败时可以通过版本协商拒绝不兼容实例，而不是产生隐式错误。

负面：

- 需要维护 golden fixtures、版本矩阵和兼容测试。
- 每个版本都要同时支持“忽略未知字段”和“拒绝未知危险枚举”，实现比单纯 `serde` 默认更细。
- 控制面在迁移期要同时服务多个主版本，增加路由和测试面。
- 不能靠镜像 tag 判断兼容性，必须持久化并校验版本元数据。

## Rejected alternatives

- 无版本 JSON：无法判断字段语义变化，升级时容易出现静默错误。
- 单一全局版本：任何小改动都要求所有核心同步升级，破坏平滑升级目标。
- 只做宽松解析：未知安全枚举可能被误当成默认值，产生错误路由或认证行为。
- 只做严格解析：新增可选字段会破坏旧核心，无法渐进升级。
