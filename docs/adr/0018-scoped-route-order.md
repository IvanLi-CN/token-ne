# 路由按作用域覆盖，顺序即语义

Status: accepted

模型路由此前是单层扁平表：所有规则同池竞争，靠 `priority` 数值排序，并叠一层"精确规则整体优先于 Glob"的隐含顺序；同时 `Model.default_upstream_model` 被当作第二层名称改写，和上游覆盖名一起推算出"有效名称"。这两件事都让所有者无法预测实际行为：拖不动、也看不出哪个规则先命中，而两层命名改写让"发往上游的到底叫什么"有三个可能来源。

我们把模型路由改为**作用域 + 顺序**：每条规则归属全局或某个上游；解析时先按上游 ID 升序逐个尝试该上游作用域，命中即锁定该上游；全部未命中再走全局作用域；两处都未命中最后按系统模型 ID 兜底。同一作用域内严格按存储顺序逐条尝试，第一条命中即生效。顺序由界面拖拽维护、整段原子提交。同时删除 `default_upstream_model`，命名转换只剩上游模型绑定这一层，即"下游请求名 → 上游路由（回落全局路由）→ 系统模型 → 绑定 → 上游模型 ID → 上游"，计费与权限始终按系统模型计算。

## Considered Options

- 保留 `priority` 数值排序：拒绝，因为用户拖拽是更自然的意图表达，而数值排序每次调整都要重写一片数字，界面与语义也对不上。
- 保留"精确规则整体优先于 Glob"：拒绝，因为叠在拖拽顺序之上后，用户把规则拖到第一位却不生效，无法解释。
- 继续用机器唯一性约束去重（exact `pattern` 全局唯一、同优先级 Glob 不可重叠）：拒绝，因为同一件事可以用多个不同表达式描述，机器无法判断哪一条应当保留；只保留"顺序可见可控"。
- 保留系统模型 ID 短路路由：拒绝，因为这让一部分请求名绕过所有者显式维护的顺序，出现无法在界面上解释的分支。
- 保留 `default_upstream_model` 作为第二层映射：拒绝，因为它与绑定竞争同一语义，且它不声明上游支持，只会制造歧义。

## 跨作用域的裁决

请求到达时网关还不知道最终服务它的上游，所以「上游作用域覆盖全局」不能按上游逐请求求值。实现固定为一条确定的尝试序列：

1. 按 `upstream_id` 稳定升序逐个上游，逐个尝试该上游作用域内的启用规则（按 `position`，第一条命中即生效）；命中即锁定该上游，并把候选限制到它。
2. 全部上游作用域都未命中，再按全局作用域的 `position` 逐条尝试；命中不限上游。
3. 两处都未命中，最后按系统模型 ID 兜底。

跨上游之间按 ID 排序是刻意的兜底而不是语义：请求名同时被两个上游作用域匹配时，机器无法判断意图，只能给出确定且可见的结果。命中上游作用域但其上游没有任何启用绑定能承接时，请求以 `503 no_upstream_available` 失败，而不是回落全局——这是所有者显式覆盖的代价，静默回落会隐藏配置错误。

## Consequences

- `model_route_rules.priority` 改为 `position`，唯一约束从"启用 exact `pattern` 唯一"改为"作用域内 `position` 唯一"；允许重复与重叠 `pattern`。
- 路由命名空间不再与系统模型 ID 互斥，目录安装的 `conflict` 分支随之消失，只剩 `created` / `exists`。
- 核心解析与预览共用同一份顺序实现；`GLOSSARY.md` 新增 **Route scope**、**Route order**，删除 **Model mapping**。
- 迁移需要一次核心配置 schema 变更：`models[]` 去掉 `default_upstream_model`，`model_routes[]` 用 `position` 取代 `priority` 并取消唯一性校验。由于这些字段替换不是增量的，`config_schema_version` 从 `1` 升到 `2`：控制面在登记、部署与推送三处都要求 `config_schema_max >= 2`，schema `1` 的核心得到可读的兼容性错误，而不是被放行后逐次收到 `422`。
- 拖拽排序成为跨作用域操作的唯一入口，需保证任一失败整段回滚，否则顺序本身会损坏。
