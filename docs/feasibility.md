# 技术可行性分析

## 结论

第一期方案可行，建议进入实施。

核心判断有三条：

1. **Rust 转发核心可以做到“内容感知的有限重试”**：在向下游提交任何响应字节之前，按 HTTP 状态、连接错误、首字节超时和 SSE 错误事件决定是否切换上游；一旦提交首个语义增量，就只透传、不再重试。这样既不破坏 OpenAI 兼容语义，也不会产生重复可见输出。
2. **Caddy 足以承担多版本流量切换**：`weighted_round_robin` 支持整数权重；当另一个上游权重为正时，权重 `0` 会停止向该上游分配新请求。Caddy 配置重载默认保留在途请求和长连接。用“权重归零 + 核心自报在途数 + 宽限期停机”可以实现可回滚的平滑升级；排水最后一个实例时必须先把 `/v1/*` 切到 `static_response` 503。
3. **Go 控制面可以安全地管理动态核心容器**：Go 通过 Docker Engine API 创建、启动、停止全部核心容器，Compose 只负责声明控制面、网络和持久依赖。控制面启动时按自身发布版本自动引导同版本 core；把 Compose 当作运行时调度器并不可靠，直接使用 Docker API 更可验证、可重试、可恢复。

主要风险不在协议实现，而在**边界纪律**：Caddy 管理面不能暴露公网，Docker socket 等价于宿主机 root，SSE 重试必须严格限定在提交前，核心配置与用量上报必须允许控制面短时不可用。

## 参考项目边界

参考项目 `codex-vibe-monitor` 采用 MIT 许可证，可以复用设计思想、协议字段和运维经验。第一期重新实现独立代码库，不直接复制其大规模运行时投影、SQLite 写入协调器、账号池和 OAuth 子系统。参考项目的价值在于已经验证过的几个机制：

- `/v1/*` 请求快照与重放，保证重试时请求体可重复发送。
- SSE 增量解析、首 Token 识别、用量提取与响应透传在同一字节流上完成。
- 首字节超时、连接失败、上游错误状态与内容错误事件的分级处理。
- 请求、上游尝试、用量和延迟分别建模，避免把“总耗时”误当 TTFT。
- 控制面与数据面分离，代理热路径不依赖数据库。

## 关键机制验证

| --- | --- | --- | --- |
| Rust HTTP 入口与上游转发 | 可行 | `axum` + `hyper`/`reqwest` 支持 HTTP/1.1、HTTP/2、流式响应和请求取消 | 需要自行控制连接超时、首字节超时、空闲超时和客户端断开 |

| 下游 Agent 重试提示 | 可行 | 重试耗尽后把可重试的上游 429/5xx、DNS/TLS/网络失败和提交前 SSE 错误映射为 503 + `Retry-After`；保留 4xx 语义 | 不能伪装成功或改写已提交状态；必须记录原始上游状态 |
| 状态码改写策略配置 | 可行 | 控制面读取 YAML/JSON，校验后随配置快照分发；未来迁入数据库和界面 | 文件无效时保留上一份有效策略；规则 schema 需要严格校验和测试 |

| Caddy 配置热更新 | 可行 | 所有变更使用完整 `POST /load`；权重和 upstream 数组同一份配置原子更新；重载默认保留在途请求 | 管理 API 无内建认证，使用 API/Caddy 共享 Unix socket；主动健康检查用 `/readyz` |

| 动态核心容器 | 可行 | Docker Engine API 支持按标签列出、创建、启动、停止、删除容器；Compose 网络可被动态容器加入 | Docker socket 等价于 root；需要 socket proxy 与网络隔离 |
| PostgreSQL 用量事实 | 可行 | 单机低到中等流量下，批量写入 + BRIN/B-tree 索引足够；30 天原始事件量可控 | 高流量需要分区或列式存储，第一期不做 |
| Prometheus 指标 | 可行 | 核心暴露内网 `/metrics` 供排障；Go 用 `client_golang` 暴露外部 `/metrics`，并从用量事件生成业务指标 | 核心指标不作为外部抓取合同；指标基数必须受控，不能把 request_id 放进标签 |
| 最新 Web 技术栈 | 可行，需兼容门禁 | React 19.3、Vite 8.3、TypeScript 7.0、Tailwind 4.3、React Router 8.5、Storybook 10.6 均为当前稳定版 | TypeScript 7 原生编译器与 Storybook/Vite 插件组合需要一次真实构建验证 |
| Bun 构建静态站点 | 可行 | Bun 1.4.5 可执行 Vite 构建；Go 用 `go:embed` 托管产物 | 构建阶段与运行阶段镜像分离，避免把 Node/Bun 带进生产镜像 |

### Caddy 的关键细节

`weighted_round_robin` 的 JSON 选择策略形如：

```json
{
  "selection_policy": {
    "policy": "weighted_round_robin",
    "weights": [100, 0]
  }
}
```

权重与 `upstreams` 数组顺序一一对应；当另一个上游权重为正时，权重 `0` 表示该上游不再接收新请求。至少一个权重必须为正；全零池无法通过 Caddy 校验。所有变更都生成完整 JSON 并 `POST /load`，保证权重和 upstream 顺序原子更新。切换时先更新权重，再等待旧版本在途请求归零，最后停止容器。排水最后一个实例时不能依赖权重 `0`：先把 `/v1/*` 切到 `static_response` 503，再停止实例。

Caddy 管理 API 使用稳定 `@id` 生成完整配置：

- 上游数组、负载均衡权重、TLS、路由和健康检查都在同一份 JSON 中。
- 不再使用 `/id/<id>/...` 分离 `PATCH`。
- 主动健康检查使用核心 `/readyz`；Docker liveness 使用 `/healthz`。

入口路由需要配置 `flush_interval: -1`，否则 SSE 可能被缓冲。Caddy 的 `grace_period` 默认为无限，配置重载不会取消已在处理的请求；这也是“权重归零后旧流还能自然结束”的前提。

Caddy 默认只提供 HTTP，不做 TLS 终止。项目部署在外部反向代理之后，由外部代理终止 TLS 并把 HTTP 转发到 Caddy 的内部端口。只有显式启用 `CADDY_TLS_MODE=auto` 时，Go 才生成 `:443` 监听、host matcher 和 `apps.tls.automation.policies`。这避免把证书管理错误地绑定进项目内部入口。

### 排水信号为什么不看 Caddy 计数

Caddy 的 `/reverse_proxy/upstreams` 返回 `num_requests`，但它是按 `dial` 地址计数，没有版本维度；旧 handler 仍存活时条目可能继续保留，清理后才消失。它不能回答“这条在途流属于哪个版本”，也不能作为跨版本排水的唯一依据。因此：

- **新请求是否还会进入旧版本**：看 Caddy 权重是否为 `0`（且池中至少另一个权重为正）。
- **旧版本是否还有在途请求**：看核心 `/internal/v1/status` 的 `inflight`。
- **何时可以停止容器**：权重归零并经过一个配置稳定窗口后，连续多次观察到 `inflight == 0`。

## 容量与性能估算

第一期按单机、单控制面、1 到 3 个核心实例估算。

| 维度 | 估算 | 说明 |
| --- | --- | --- |
| 核心并发流 | 200 到 500 条/实例 | 2 vCPU、1 GiB 内存；受上游延迟和客户端消费速度影响 |
| 核心内存 | 每条流缓冲上限约 256 KiB 预提交 + 64 KiB 行缓冲 | 500 条流最坏约 160 MiB，另加连接和 JSON 开销 |
| 代理附加延迟 | p95 小于 10 ms（非流式），TTFT 附加 p95 小于 20 ms | 不含上游时间；以本地 mock 上游基准测试 |
| 日请求量 | 100 万条/日以内可直接使用 PostgreSQL 单表 | 约 10 请求/秒；批量写入按 250 ms 或 500 条聚合 |
| 30 天用量行数 | 约 3000 万行 | 需要 BRIN（时间）与少量 B-tree 索引；超过 500 万行/日时改为按月分区 |
| Caddy 吞吐 | 远高于第一期需求 | Caddy 不是瓶颈；瓶颈通常在上游和 PostgreSQL 写入 |
| Go 控制面 | 单实例足够 | 用量摄入、配置推送、Caddy 协调、Docker 协调均为低频操作 |
| 核心 usage spool | 默认 8 GiB / 24 小时 | 单条约 0.8 到 1.5 KiB；10 请求/秒可用超过 24 小时，100 请求/秒接近 24 小时 |
| 配置传播 | 小于 5 秒 | Go 推送 + 核心原子切换；失败时保留上一版配置 |

这些数字是工程预算，不是承诺。第一期验收用压测确认 50 条并发 SSE 流、10 分钟持续运行、无内存持续增长。

## 方案取舍

| 议题 | 推荐方案 | 备选 | 结论 |
| --- | --- | --- | --- |
| 流量切换器 | Caddy 加权轮询 + 管理 API | Envoy + xDS | Caddy 已满足需求；Envoy 的控制面和配置复杂度远超第一期 |
| 核心编排 | Go 调 Docker Engine API；动态容器带 Compose 项目标签和网络，属于项目成员但不是声明服务 | Go 调 `docker compose` CLI 动态改文件 | Compose CLI 不适合作为运行时调度器；并发、半失败和自改项目文件都难以恢复。项目成员关系由标签保证（必须包含 `com.docker.compose.config-hash`）；整机下线时 `down --remove-orphans` 可清理，单实例用控制面 prune |
| Caddy 配置来源 | Go 生成完整 JSON，通过管理 API 装载 | Caddyfile + `caddy-docker-proxy` 标签发现 | 标签发现无法精确表达权重、排水和回滚；JSON 管理 API 可验证 |
| Caddy TLS | 默认只监听 HTTP，外部反向代理终止 TLS | Caddy 自动 HTTPS | 本项目入口在受控网络内；TLS 生命周期由宿主代理负责，避免证书与项目内路由耦合 |
| 请求重试位置 | Rust 核心做内容感知重试 | Caddy 重试 | Caddy 看不到 SSE 内容，也无法安全重放已读取的 POST 体 |
| 核心配置来源 | Go 推送 + 核心本地加密缓存 | 核心直连 PostgreSQL | 核心直连数据库会把数据面耦合到数据库凭据和 schema |
| 用量传输 | 核心 HTTP 批量推送 Go | 核心直写 PostgreSQL；OpenTelemetry Collector | HTTP 批量最简单，schema 单一所有者；OTel 留到需要跨系统追踪时 |
| 控制面不可用时的用量缓冲 | 核心私有分段 usage spool（只存用量元数据），由 core 自行重放 | Redis Streams / NATS / Kafka | 单机第一期不需要额外 MQ；spool 无新服务、可跨容器重启、满足 3 到 24 小时缓冲；控制面不读取文件。跨宿主机持久化再上 MQ |
| 核心配置缓存 | 控制面推送，本地加密缓存；签名可选且默认只告警；手动 override 可启动 | 核心直连数据库；强制签名启动门 | 核心不碰数据库；缓存和 override 提供紧急恢复能力；不支持从未被控制过的纯冷启动 |
| 业务存储 | PostgreSQL | ClickHouse | 第一期数据量不需要列式数据库；先保证正确性和运维简单 |
| 指标存储 | Go `/metrics` 作为唯一外部抓取目标；核心内部 `/metrics` 仅排障 | 核心各自暴露指标由外部抓取 | 外部 Prometheus 无法可靠解析 Compose DNS；Go 聚合后只暴露一个抓取目标 |
| 静态站点托管 | Go `go:embed` 托管构建产物 | 独立 Nginx；Caddy `file_server` | 单镜像原子发布，减少一个服务；Caddy 只做入口 |
| 数据库中的上游密钥 | AES-256-GCM 加密 | 外部 Vault/SOPS | 第一期用主密钥加密；主密钥独立备份，后续可接 Vault |
| 官方渠道号池 | 第一期只做 API Key 上游 | 直接做 OAuth 账号池 | 先把路由、观测、升级闭环跑通；schema 预留 `kind` 扩展 |

## 主要风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Caddy 管理 API 无认证 | 内网容器可改全部路由 | 使用 API 与 Caddy 共享的 Unix socket，不监听网络；API 是唯一调用方；入口显式拒绝 `/internal/*` |
| Docker socket 权限过大 | 控制面被攻破等价于宿主机 root | 使用 socket proxy 限定容器/镜像/网络接口；控制面不暴露公网；后续可拆独立 `core-controller` |
| 重试导致重复输出 | 下游看到重复 token | 只在提交前重试；提交后无论是超时、断开还是上游错误都只透传 |
| 状态码改写过宽 | 隐藏不可重试错误，延长故障 | 只改临时类别；400/401/403/404/409/422 保持原样；原始上游状态和改写指标可见 |
| 状态码策略文件无效 | 规则未生效或行为回退 | 控制面保留上一份有效策略并告警、增加 `status_rewrite_policy_invalid_total`；只有从未有过有效策略时才使用内置默认 |
| SSE 注入 `include_usage` 改变客户端可见流 | 客户端多收到一个 usage chunk | 该行为可配置；默认开启并写入文档；对 responses API 优先从完成事件解析 |
| 长流阻塞升级 | 旧版本长时间无法下线 | 权重归零后等待在途归零；设置最大等待（如 30 分钟），超时强制停止并记录审计 |
| Caddy 计数没有版本维度 | 误判旧版本可停 | 排水只看核心 `inflight`；Caddy 计数只作辅助诊断 |
| PostgreSQL 写入放大 | 高频插入拖慢查询 | 批量写入、只保留必要索引、30 天保留；超过阈值再分区或引入列式存储 |
| 指标基数爆炸 | Prometheus 内存和查询恶化 | 标签只允许 model、upstream、status、core_version 等低基数维度 |
| TypeScript 7 / Vite 8 / Storybook 10 组合不兼容 | 前端无法构建 | 初始化时跑一次真实构建门禁；不通过则降级到 TypeScript 5.9，保持其他最新主版本 |
| 上游 URL 可配置导致 SSRF | 控制面可被用来访问内网 | 默认只允许 `https` 和公网地址；开发模式显式放开；核心二次校验 |
| 控制面不可用 | 无法改配置或部署 | 核心使用本地配置缓存继续服务；用量写入核心私有 spool，core 自行重放；默认保留 24 小时 |
| 用量 spool 写满 | 控制面长期不可用时可能丢失旧用量 | 按 `spool_max_bytes` 和 `spool_max_age_hours` 限制；删除最旧未确认段并记录 `spool_dropped_total`；容量按峰值请求量预估 |
| 配置缓存过期或被吊销 | 控制面不可用时仍按旧 Key/上游服务 | 缓存只在被控制面成功控制过后有效；记录 `config_age` 并告警；需要立即吊销时停止实例，而不是依赖缓存自动失效 |
| 手动 override 引入错误配置 | 核心按错误路由/密钥启动，可能泄漏或失败 | override 只用于紧急恢复；启动日志高优先级告警、指标可见、审计记录；操作者恢复后删除文件并重新由控制面推送 |
| 配置签名被误认为安全门 | 操作者以为签名能阻止篡改 | 签名默认只告警，用于发现损坏/误改；真正的配置写入权限由状态目录权限和控制面 Token 控制 |
| 宿主机整体故障 | 本地 spool 和配置缓存一起丢失 | 第一期只保证控制面故障和容器重启；跨宿主机持久化需要外部队列或对象存储，明确不在第一期 |

## 已确认的默认决策

以下决策已经确认并写入 PRD、架构和 ADR：

1. **用 Docker Engine API 代替 Compose CLI 做动态核心编排**。动态容器带 `com.docker.compose.project`、`service`、`oneoff`、`config-hash` 等标签，仍是 Compose 项目成员，但不是 Compose 文件里声明的 service。整机下线时 `docker compose down --remove-orphans` 可以清理；`docker compose up` 不会重建它们；单实例清理使用控制面 prune。若要求“必须是声明服务”，需要改成 Compose CLI 编排，不推荐。
2. **第一期不保存请求/响应正文**。只保存用量、延迟、状态、错误分类和截断后的错误消息，降低隐私与存储风险。
3. **Caddy 默认只监听 HTTP，不终止 TLS**。TLS 由宿主上的外部反向代理负责；只有显式启用 `CADDY_TLS_MODE=auto` 时，Go 才生成 443 监听和自动 HTTPS 配置。
4. **chat.completions 流式请求默认注入 `stream_options.include_usage=true`**，以保证可计费用量；该行为可在上游或全局配置中关闭。
5. **第一期只支持 API Key 上游**，不做 OAuth 登录、账号配额窗口、自动轮换和号池健康评分。
6. **控制面不可用时，用量写入核心私有 spool，默认保留 24 小时，由 core 自行重放**。控制面不读取文件；已停止实例用兼容 core 重启后自愈。宿主机整体故障不在第一期保证范围内。
7. **配置签名默认只告警，手动 override 可以启动但会记录高优先级警告**。签名不作为不可绕过的启动门；它只用于发现损坏或误改。
8. **状态码改写策略第一版来自 YAML/JSON 文件，由控制面校验并随配置快照分发**。后续迁入数据库和 Web 编辑器；无效文件保留上一份有效策略，只有从未有过有效策略时才使用内置安全默认。
9. **模型是全局实体，不按上游拆分**；上游通过显式能力关系参与候选，名称改写按上游覆盖 → 全局映射 → 原模型名的继承规则。
10. **Caddy 配置统一全量 `POST /load`，主动健康检查使用 `/readyz`**；不再用分离的 PATCH 更新权重或 upstream。
11. **Compose 网络分为 `edge`、`core-control`、`data`**；Caddy 管理面走 API 与 Caddy 共享的 Unix socket；core 不能访问 Caddy 管理面、Docker socket 或 PostgreSQL。

## Go / No-Go

**Go。** 没有发现阻塞第一期的技术缺口。需要在实施早期验证的六件事：

- 用真实 Caddy 2.11.9 验证“权重归零 + 配置重载 + 长 SSE 不被掐断”。
- 用 mock 上游验证 SSE 预提交重试不会产生重复内容。
- 用 TypeScript 7 + Vite 8 + Storybook 10 跑通一次前端构建。
- 杀掉控制面 24 小时模拟：核心继续服务、用量 spool 增长、恢复后重放且不重复。
- 模拟配置损坏或控制面不可用：手动 override 能启动、只输出告警、不伪造 `last_controlled_at`。
- 修改状态码改写 YAML/JSON：有效变更自动推送；无效文件保留上一份有效策略并告警。

这些都属于可快速证伪的实验，不需要重构架构。
## 第二期可行性与风险

第二期不要求改变数据面与控制面的总体边界。模型目录同步和第三方价格获取由控制面执行；core 只消费已审核的路由、上游策略、能力和名称映射快照，因此目录或价格源故障不会直接阻塞请求热路径。

| 机制 | 可行性结论 | 主要风险 | 推荐缓解 |
| --- | --- | --- | --- |
| 上游 `/v1/models` 同步 | 可行 | 上游列表短暂缺失或格式变化导致误删能力 | 保留最后成功快照；缺失只标记 stale；同步不自动启用能力 |
| 白名单/黑名单 Glob | 可行 | 规则重叠、大小写和实现语言不一致 | 只支持完整字符串 Glob；控制面保存前校验；core 使用同一规则 fixture |
| 模型名称路由 | 可行 | 模糊规则产生非确定性或绕过 Key 权限 | 精确全局 ID 优先；priority 决定 Glob；歧义写入失败；先解析再做 Key 权限 |
| 上游级价格 | 可行 | 同名模型不同上游价格导致历史成本解释困难 | 上游级覆盖优先；写入 `price_revision_id`；不重算历史 |
| 第三方价格源 | 可行 | SSRF、源格式漂移和错误批量覆盖 | 首版只用受控内置适配器；获取、预览、应用分离；人工锁定优先 |
| 旧 core 兼容 | 可行但需门禁 | 旧 core 静默忽略新路由或策略 | meta 能力协商；不支持所需能力的 core 保持权重 0 |

第二期实施前应先用 mock 上游验证目录同步失败保留旧状态、Glob 冲突拒绝、别名权限检查、上游级价格选择和价格报价原子应用。这些验证不需要引入新的基础设施。
